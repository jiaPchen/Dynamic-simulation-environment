# 阶段二仿真测试系统框架与运行指南

## 1. 系统目标与边界

本目录对应《项目推进》中的阶段二：使用 TruckSim、Simulink 与 Python 建立三轴车辆的闭环联合仿真，并以 TXT 测试用例驱动单工况或批量试验。

系统的目标是：让第一轴的阶跃或正弦转向输入经 Python 的“零质心侧偏角多轴转角分配控制器”计算为六路车轮转角，送入 TruckSim；同时记录车辆状态、控制器状态、曲线与 Word 测试报告。

系统边界如下：

- MATLAB 脚本是实际运行入口；TruckSim 负责车辆动力学，Python 不替代 TruckSim 模型。
- TXT 用例当前可配置停止时间、初始/目标车速、路面附着系数和转向激励。
- Word报告是运行结果的可读汇总：它可以判断运行完整性，但在没有统一控制效果阈值时，控制性能保持`NOT_EVALUATED`。

```text
TXT 测试用例
      │
      ▼
MATLAB 入口脚本
      │  ├─ 解析与校验用例
      │  ├─ 启动 Python TCP 服务并配置 TruckSim
      │  └─ 启动 Simulink 仿真
      ▼
Simulink：TruckSim S-Function ←→ TCP Client S-Function ←→ Python TCP 服务
      │                                                    │
      │  返回 Vx、beta、横摆角速度                         └─ 计算 6 路转角
      ▼
CSV / 日志 → PNG 曲线 → 单工况或批量 Word 报告
```

## 3. 实际执行流程

### 3.1 单工况

1. `run_case_python.m` 默认选定 40 km/h 阶跃 TXT；如需其他用例，先修改 `caseFile`，再调用 `run_single_python_case`。
2. MATLAB 解析 TXT，校验必填字段和数值范围，加载 Simulink 模型，并设置 TruckSim S-Function 的 `SIMFILE`。
3. MATLAB 在本机 `127.0.0.1:50007` 启动可追踪的 Python TCP 服务进程。原 TXT 会复制到临时目录，但保留与 `case_name` 相同的文件名；异常时入口会清理整个服务进程树。
4. Python 读取 YAML 和 TXT，尝试写入 TruckSim 工况。严格模式下只有日志出现 `CONFIG_READY` 才会继续。
5. Simulink 与 Python 完成 `HELLO → READY` 握手，并核对协议号、接口版本、单位和固定 0.01 s 控制周期；随后交换 `STATE → CONTROL`。状态为 `[Vx_kmh, beta_deg, w_degps]`，控制量为 `[d1L,d1R,d2L,d2R,d3L,d3R]`。
6. MATLAB 用 TXT 的 `stop_time_s` 调用 Simulink；结束后导出 TruckSim/Simulink 信号，并把 Python 信号日志复制到同一运行目录。
7. Python 读取 CSV，输出曲线、指标 CSV、清单和单工况 Word 报告。

报告程序会进一步计算`execution_status`。只有运行状态为`COMPLETED`、时间轴覆盖设定时长、必需信号均为有限值、TCP生命周期标记完整且TruckSim配置为`CONFIG_READY`时，运行完整性才为`PASS`。该结果只表示联仿流程和数据完整，不代表控制性能通过验收。

### 3.2 批量

`run_batch_python` 对 `02_测试用例/` 中每个 TXT 重复单工况主流程，但关闭单工况 Word 报告。每个工况独立记录 `COMPLETED/ERROR/SKIPPED`；默认失败后继续。完成后写入 `批量运行状态.csv` 和 `batch_run_dirs.txt`，由 `make_batch_summary.py` 输出唯一的批量 Word 与指标汇总 CSV。

若某工况在 Python 服务启动、联仿或导出过程中失败，会在当前批次的 `failed_cases/` 下新建诊断目录，保留用例副本、可取得的 Python 日志与错误堆栈；`批量运行状态.csv` 的 `run_dir` 指向该目录。失败工况不会混入仅包含成功运行目录的 `batch_run_dirs.txt`，也不会被误计为控制性能通过。

批量模式不是并发执行：各用例顺序运行，使用阶段二专用Run。运行期间不要同时手动启动另一套仿真；即使入口文件不同，同时写同一个TruckSim数据集也可能发生冲突。

## 4. 用例格式、控制参数与传递关系

每个 TXT 至少应包含：

```text
schema_version = 3
case_name = <唯一名称>
stop_time_s = <正数>
initial_speed_kmh = <车速>
steer_input_type = step 或 sine
```

常用字段：

| 字段 | 作用 | 实际去向 |
| --- | --- | --- |
| `stop_time_s` | Simulink 停止时间 | MATLAB `sim(..., 'StopTime', ...)`；TruckSim `TSTOP` |
| `initial_speed_kmh` / `target_speed_kmh` | 初始/目标速度 | 求解器读取 `SPEED_TARGET_CONSTANT`；源 Procedure 中的 `*SPEED` 仅为界面元数据。当前专用 Run 尚未验证独立初速度映射，因此两值不同时配置会失败，不会误报 `CONFIG_READY` |
| `steer_input_type`、幅值、频率、开始时间 | 第一轴阶跃或正弦激励 | Python 控制器 |
| `control_dt_s` | 控制器周期 | Python 服务与控制器；当前用例均为 0.01 s |
| `kp_beta` / `ki_beta` / `max_steer_deg` | PI 反馈和转角限幅 | 覆盖 YAML 默认控制器参数 |
| `road_friction` | 目标绝对路面附着系数 | 仅写`MY_FRICTION=road_friction/road_base_mu`；不改道路文件的`MU_ROAD_CONSTANT` |
| `road_grade` | 纵坡百分数，`5` 表示上坡 5% | `straight_road` 写 `ROAD_ZS_COEFFICIENT 0.05`；`hill_20deg` 要求该值为 0 |
| `trucksim_scenario` | 道路高程场景 | `straight_road` 为可设均匀纵坡的直线路面；`hill_20deg` 为 TruckSim 2019 示例起伏高程表 |

控制器的第一轴来自用例；第二、三轴由速度相关前馈和质心侧偏角 PI 反馈共同决定，六个轮端输出按同轴左右相同的接口顺序发送给 TruckSim。

当前正式目录有 4 个样例：15 km/h 正弦、40 km/h 正弦、20 km/h 阶跃和 40 km/h 阶跃。每个 TXT 的文件名、`case_name` 和 `source_case_id` 均唯一；新增用例时必须继续保持这一约束。

这些是《项目推进》阶段二当前的常规阶跃/正弦验证用例。非零坡度、起伏高程和 COM 实测可作为扩展试验，但不是这份阶段任务的必验项；不能把离线配置回读解释为真实车辆响应已验证。

## 5. TruckSim 配置机制

`trucksim_com.py` 有两层机制；当前 YAML 默认优先使用能直接改变 S-Function 输入的 `.par` 配置：

1. `prefer_par_file_patch: true` 时，程序从阶段二专用入口的`INPUT`行定位`Run_all.par`，写入停止时间、速度、附着系数倍率和道路高程参数，并递归修补关联的 Procedure/Event 参数。`straight_road` 使用均匀纵坡系数，`hill_20deg` 使用内置示例高程表；切换工况时会替换阶段二标记块，防止上一工况的坡度残留。写入后回读核对；未知场景、冲突坡度或异常道路块会失败，不输出 `CONFIG_READY`。
2. 只有显式关闭优先 `.par` 配置时，才尝试 `com_progids` 中的 COM 接口。当前机器的候选 ProgID 未注册，COM 路径不能用于本机验收。

附着系数只更新 `MY_FRICTION`，不改共享道路文件的 `MU_ROAD_CONSTANT`；道路高程也只写阶段二专用 `Run_all.par`，不改共享 `Roads/*.par`。被修改的文件会生成 `.phase2_backup` 备份。`hill_20deg` 的路径仍是当前直线参考线，只改变高程，并非独立曲线路面。坡度/场景已通过离线回读测试，但真实车辆响应仍需另行做低速联仿验证。
TruckSim 界面中的原始道路数据集仍会显示平路；本次实际求解参数应以专用 `Run_all.par` 和 Python 配置日志为准。重新“发送到 Simulink”可能重建 `Run_all.par`，但下一次脚本运行会按 TXT 再配置。

均匀纵坡的低速验证用例位于 `05_python_controller/tests/fixtures/road_grade_5pct_15kmh.txt`，不在常规批量目录内。验证固定起伏路面时，可复制该用例并设 `trucksim_scenario = hill_20deg`、`road_grade = 0`。先单工况检查日志里的高程回读，再看车辆纵向/垂向响应；不要把未经验证的起伏场景直接加入常规高速批量测试。

当前电脑配置在代码中使用：

```text
Python:     C:\Python\python\python3.10.4\python.exe
TruckSim:   C:\Trucksim2019\TruckSim2019.0_Prog\Programs\solvers
项目路径记录: <阶段二项目根目录>\runtime\trucksim_phase2.path（指向数据目录中的simfile_phase2.sim）
TCP 端口:   50007
```

换电脑必须在导入阶段二cpar并“发送到Simulink”后运行`capture_phase2_simfile`，再检查Python和solver路径；详细步骤见`03_换机配置与AI交接说明.md`。

## 7. 输出、追溯与结果解释

单工况通常产生：

```text
03_数据存储/Python联仿/<运行编号>/
  <运行编号>_trucksim_io.csv        # MATLAB/TruckSim 状态与实际输入
  <运行编号>_python_signals.csv     # TCP 服务收到的状态与计算的转角
  <运行编号>_case.txt               # 用例快照
  <运行编号>_case_info.csv          # 用例元数据
  <运行编号>_metrics.csv            # 指标
  <运行编号>_python_stdout.log      # 配置与通讯日志
```

批量结果位于 `04_测试报告/批量仿真_<时间>/`，含 `cases/`、`figures/`、`批量运行状态.csv`、`batch_run_dirs.txt`、`批量指标汇总.csv` 和 `阶段二批量仿真测试报告.docx`。

当前保留的最近一次常规批次为 `批量仿真_2026年09月25日_14时38分10秒_290毫秒`：四工况均 `COMPLETED`、`execution_status=PASS`，四份日志的 `CONFIG_READY`、`HANDSHAKE_OK`、`STOP_OK`、`SERVER_STOPPED` 均齐全，批量指标汇总中的采样周期均为 0.01 s。同一时间的第 042 次单工况也有对应数据和报告。这只证明当次运行和数据完整；换机后须重新预检与试跑，控制性能仍按下表单独解释。

结果状态不要混用：

| 字段 | 含义 | 当前用途 |
| --- | --- | --- |
| `run_status` | MATLAB编排是否完整结束 | `COMPLETED/ERROR/SKIPPED`等运行状态 |
| `execution_status` | 时间轴、信号、TCP生命周期和TruckSim配置是否完整 | 报告中的运行完整性`PASS/FAIL` |
| `acceptance_status` | 控制性能是否满足规定阈值 | 当前为`NOT_EVALUATED`，待项目定义统一阈值后启用 |

结束车速偏差、质心侧偏角、横摆角速度和各轴转角均为客观指标。未配置判定阈值时，即使数值值得关注，也不能由报告程序擅自标记控制性能PASS或FAIL。

## 8. 故障定位顺序

1. 预检失败：先核对Python、TruckSim solver、`runtime/trucksim_phase2.path`及其指向的`simfile_phase2.sim`、模型路径与依赖。
2. 服务启动失败：查临时 `server_stdout.log`，关注 `CONFIG_FAIL`、端口占用或 Python 模块缺失。
3. 仿真启动失败：确认模型内块名与`run_single_python_case.m`中默认名称一致，且TruckSim S-Function与Python均使用`runtime/trucksim_phase2.path`记录的同一份阶段二专用simfile。
4. 工况未生效：查运行目录 `*_python_stdout.log` 的 COM/`.par` 修改记录，并用报告或 CSV 的初始速度复核。
5. 无报告或曲线：先确认两类 CSV 是否完整，再单独运行报告脚本定位 Python 依赖或中文字体问题。
6. 时间分析异常：比较 `*_python_signals.csv` 与 `*_trucksim_io.csv` 的 `sim_time_s` 末值，并检查 `case_info.csv` 中的 `export_time_source`、`raw_out_tout_end_s` 与 `tcp_sim_time_end_s`。不能只因时间来源显示为 `python_tcp_sim_time_s` 就判定通过；两份 CSV 的末时间都必须与 `stop_time_s` 一致。
