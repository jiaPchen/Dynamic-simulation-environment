# 阶段二仿真测试系统全景梳理

> 目的：说明当前 `动力学仿真环境阶段二` 文件夹中的真实资产、控制链路、数据链路、结果边界和维护重点。

## 1. 一句话总览

阶段二是一个由 MATLAB 脚本编排的单机联合仿真系统：TXT 用例定义工况，Python 服务按零质心侧偏角控制律计算三轴六轮转角，Simulink 在 TCP 中转状态和控制量，TruckSim 计算车辆响应，最后由 MATLAB/Python 导出 CSV、绘制曲线并生成 Word 报告。

```text
TXT case
   │
   ▼
run_case_python.m / run_batch_python.m
   │
   ├─ run_single_python_case.m ── 解析用例、设置模型、启动 Python
   │                                      │
   │                                      ▼
   │                            tcp_server.py
   │                            ├─ 配置 TruckSim
   │                            └─ zero_sideslip_controller.py
   ▼                                      ▲
Simulink 模型 ── TruckSim S-Function ── TCP Client S-Function
   │                                      │
   └──────── out / CSV ───────────────────┘
                     │
                     ▼
make_report_python.py / make_batch_summary.py
                     │
                     ▼
CSV、PNG、DOCX
```

## 2. 本目录范围

本文只解释 `01_trucksim_simulink_python/` 内的阶段二文件。该目录自身包含运行所需的 Simulink 模型、MATLAB 脚本、TXT 用例、Python 控制器、历史数据和报告；日常运行根目录即为本目录。

阶段一和阶段二各保存自己的项目内simfile入口，并必须指向不同Run；同一时刻仍只允许一个实例修改同一套TruckSimRun及关联`.par`参数文件。

## 4. 控制与数据如何流动

### 4.1 工况参数流

```text
*.txt
  ├─ MATLAB parse_case.m：本地校验
  ├─ Python parse_case_py.py：服务端校验
  ├─ run_single_python_case.m：设置 StopTime
  ├─ tcp_server.py：设置控制周期并加载控制器
  └─ trucksim_com.py：配置 TSTOP、速度、附着系数、坡度和道路高程场景
```

YAML 提供车辆几何、质量、惯量、轮胎等效侧偏刚度、默认控制器增益和道路场景映射。TXT 内的 `kp_beta`、`ki_beta`、`max_steer_deg` 可以覆盖相应默认值。`road_grade` 的单位为百分数（`5` 表示 5%），在直线路面场景写为 `ROAD_ZS_COEFFICIENT 0.05`；`hill_20deg` 是固定高程表场景，要求 TXT 的 `road_grade=0`。每次配置都会覆盖前一工况的高程定义。

### 4.2 运行时闭环

1. Python 服务先配置 TruckSim，再监听本机 TCP 端口 50007。
2. Simulink Client 发送 `HELLO`，声明协议版本、3 个输入名称与 6 个输出名称；Python 校验后回复 `READY`。
3. 每 0.01 s，Simulink 发送 `STATE(step_id, t, [Vx_kmh,beta_deg,w_degps])`。
4. Python 验证连续步号和有限数值，计算 `CONTROL(step_id, t, [d1L,d1R,d2L,d2R,d3L,d3R])` 并立即记录一行 `python_signals.csv`。
5. Simulink 把控制量接入 TruckSim；模型结束时发送 `STOP`，Python 写入 `STOP_OK` 和 `SERVER_STOPPED`。

这种握手与逐步编号的意义是：维度不一致、协议不一致、非有限状态或漏步都会让服务报错，而不会静默输出看似正常的控制量。

### 4.3 TruckSim 工况写入

当前 `vehicle_config.yaml` 设定 `prefer_par_file_patch: true`，配置层默认直接使用阶段二专用 `.par` 文件路径；关闭这一优先设置后才尝试尚未在本机验证的 COM 接口。程序会从项目内阶段二入口的 `simfile` 找到当前 `INPUT` 的 `Run_all.par`，并追踪 `ENTER_PARSFILE`、`PARSFILE` 与事件引用。附着系数只通过 `MY_FRICTION` 倍率写入，不修改道路文件的基准 `MU_ROAD_CONSTANT`。

这条机制的前提是：Simulink S-Function 与 YAML 指向同一个 TruckSim 数据目录。二者不一致时，日志即使显示配置成功，也可能不是模型正在使用的工况。

## 6. 报告如何得出

`make_report_python.py` 会读取同一运行目录的 TruckSim IO、Python 信号和用例快照。它优先以 Python 的 `sim_time_s` 合并时间轴，再补充 TruckSim 状态；随后计算采样点数、采样周期中位数、起止/最大车速、结束车速偏差、最大质心侧偏角、最大横摆角速度和三轴转角峰值，生成七类曲线、完整指标CSV和Word报告。写指标文件时会保留已有的额外追溯字段，不再用精简字段覆盖完整指标。

`make_batch_summary.py` 逐个加载批次中的运行目录，复制每个工况的曲线并输出汇总表。因此批量Word的数值来源仍是各case的CSV，不会重新运行仿真。批量报告会给出每个工况的运行完整性和最终批量结论。

报告状态分为三层：`run_status`表示编排流程是否完成；`execution_status`根据运行状态、时间覆盖、必需信号、TCP生命周期和TruckSim配置判定`PASS/FAIL`；`acceptance_status`表示控制性能验收。当前没有统一控制效果阈值，因此控制性能保持`NOT_EVALUATED`。运行完整性PASS不能解释为控制性能已经验收通过。

这意味着：报告是“数据的可视化和汇总”，而非第二套独立测量。若源 CSV 的时间轴或信号映射错误，报告也会继承该错误或掩盖该错误。

## 7. 推荐使用顺序

1. 先阅读 `03_换机配置与AI交接说明.md`，核对本机的MATLAB、Python、TruckSim solver和`runtime/trucksim_phase2.path`记录的专用入口。
2. 在MATLAB运行`run_local_preflight`，确认模型、S-Function、Python依赖和阶段二专用TruckSim入口都存在。
3. 运行 Python 离线控制器与 TCP 测试。
4. 若换机后先跑低速单工况，将 `run_case_python.m` 的默认 `caseFile` 切换为现有 15 或 20 km/h 用例；复核日志中的 `CONFIG_READY` 和导出 CSV 的初始速度。当前默认 40 km/h 阶跃不应被误认为低速首测用例。
5. 对同一次单工况比较 Python 与 TruckSim IO 的时间末值；时间轴一致后再运行全部批量。
6. 仅在 CSV、日志、曲线和 Word 都齐全且关键时间/速度检查通过后，再把结果用于技术结论。

## 8. 推荐的后续完善方向

- 当前导出代码已检查车辆状态和 Python TCP 时间轴对 `stop_time_s` 的覆盖，并以 TCP 时间轴对齐正式 CSV；新增或修改工况后继续核对两份 CSV 的首末时间、行数与关键转角/状态，不把已有检查再写成待实现功能。
- 当前 4 个 TXT 的 `case_name` 和 `source_case_id` 均不同；新增用例时保持唯一。若后续需要批量汇总直接显示 `source_case_id`，再扩充汇总 CSV 字段；当前批次仍可从各工况用例快照追溯。
- 若项目负责人需要正式控制性能 `PASS/FAIL`，先为相应测试确定指标和阈值；《项目推进》本身未提供数值阈值，配置或数据异常继续由运行状态和运行完整性单独表达。
- 把本机绝对路径集中为一份机器配置，减少换机时多脚本、多 YAML 同步修改的风险。

非零坡度、起伏路面、COM 实测，以及统一主模型或共享 Excel 工况库属于扩展/后续方案范围，不是《项目推进》阶段二现有四工况完成与否的判据。
